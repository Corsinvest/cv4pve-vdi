# Internationalization (i18n)

cv4pve-vdi can be used in several languages. The UI culture is picked from the **login window** (globe icon next to the title) and persisted in `config.yaml` (`language: auto`, `language: it`, ...). Picking **Auto** follows the operating system's culture.

## How language selection works

- All UI strings come from `.resx` resource files in [`src/Corsinvest.ProxmoxVE.Vdi/UI/Resources/`](../src/Corsinvest.ProxmoxVE.Vdi/UI/Resources)
- `Strings.resx` is the **base** (English) — every key the application uses lives here
- `Strings.<culture>.resx` (one per language, e.g. `Strings.it.resx`) provides translations
- Missing keys in a translation file fall back to `Strings.resx` automatically
- Switching language in the login combo recreates the window immediately — no restart required

## Currently available languages

The current set is whatever ships in the [Resources folder](../src/Corsinvest.ProxmoxVE.Vdi/UI/Resources). At the time of writing this includes English, Italiano, Deutsch, Français, Español, Português (Brasil), Русский, Polski, Nederlands and Čeština — but the source of truth is the folder.

## Translations welcome

Translations are open to community contributions, and **pull requests improving existing translations or adding new ones are very welcome** — especially for languages we maintain via machine translation today (currently Polish, Czech, Russian and partially German / Dutch may benefit from native-speaker review).

### Improving an existing translation

1. Open `src/Corsinvest.ProxmoxVE.Vdi/UI/Resources/Strings.<culture>.resx`
2. Adjust the `<value>` for any key that reads awkwardly
3. Open a pull request — even small terminology fixes are valuable

### Adding a new language

1. **Copy** `Strings.resx` to `Strings.<culture>.resx` using a standard culture code:
   - Short form: `it`, `de`, `nl`, `pl`, `cs`, `ja`, `zh-Hans` ...
   - Region-specific: `pt-BR`, `zh-Hant`, `es-MX` (only when truly different from the generic culture)
2. **Translate every `<value>`**, keeping the `name=` attribute exactly as it appears in the base file. Don't touch the XML schema, headers or `<data>` keys.
3. **Add the language to the picker**: open `src/Corsinvest.ProxmoxVE.Vdi/UI/LoginWindow.cs` and add a row to the `Languages` array, keeping the alphabetical order by endonym:
   ```csharp
   ("ja",    "日本語"),
   ```
   The label is the language **endonym** (its name written in itself), so users always recognise it regardless of the current UI culture.
4. **Build** the project. MSBuild compiles the new `.resx` into a satellite assembly (`<culture>/cv4pve-vdi.resources.dll`) automatically. No code changes are needed beyond steps 2-3.
5. **Try it**: launch the app, pick the new language from the login combo, and walk through every window (login, main, settings tabs, kiosk prompt, dialogs) to catch missing translations or overflows.
6. **Open a pull request** with the new file and the `Languages` row.

> [!TIP]
> Use [DeepL](https://www.deepl.com/) or a similar tool for a fast first pass, then go through every key making sure the technical context is right. Words like *Cluster*, *Node*, *Container*, *Launcher*, *Guest agent* are domain-specific Proxmox terminology — they're often left untranslated even in localised UIs.

## Notes for translators

A few stable conventions used across translations — feel free to deviate when the target language has a more natural choice:

| English | Suggested treatment |
|---|---|
| `Cluster`, `Node`, `Pool`, `Tag` | Keep as-is or close transliteration — Proxmox terminology |
| `Container` / `CT` | Keep `CT` as a short label; localise `Container` only if natural |
| `Launcher` | Localise if a natural term exists, otherwise keep |
| `Guest agent` | Usually kept as English compound (Proxmox-VE wording) |
| `Kiosk` | Localise to local equivalent (e.g. `Quiosco`, `Kiosek`) |
| `SPICE`, `VNC`, `OK`, `OTP` | Acronyms, never translated |
| `Proxmox VE VDI Client` | Product name, never translated (hard-coded outside `.resx`) |
| Tab section headers (`FILTERS`, `STATUS`, ...) | All-caps in source, follow the local convention (German doesn't capitalise like English) |

## Adding new keys

When the application gains a new string, add it only to `Strings.resx` first. Translators (or future PRs) will then add the matching `<data>` entries to the other resx files. The ResourceManager fallback ensures the app never crashes on a missing key — it shows the English string instead.
